OBJECTIF TECHNIQUE

Adapter les panneaux de recrutement pour que les unités soient affichées selon le niveau de caserne :

Sans caserne :
- afficher une bannière claire :
  “Construisez une caserne pour recruter des unités.”
- les unités restent visibles ou regroupées, mais les boutons de recrutement sont désactivés.
- indiquer le niveau requis.

Caserne niveau 1 :
- unités N1 recrutables si ressources suffisantes et production disponible.
- unités N2/N3/N4 visibles mais verrouillées.

Caserne niveau 2 :
- unités N1/N2 recrutables.
- unités N3/N4 verrouillées.

Caserne niveau 3 :
- unités N1/N2/N3 recrutables.
- unités N4 verrouillées.

Caserne niveau 4 :
- toutes les 15 unités visibles/recrutables selon ressources et production existantes.

À FAIRE — client

1. Ajouter un mapping UI des niveaux requis

Dans RecruitmentPanel.tsx, ajouter une constante locale ou réutilisable :

BARRACKS_REQUIRED_LEVEL_BY_UNIT = {
  militia: 1,
  garrison: 1,
  scouts: 1,
  hunters: 1,

  patrollers: 2,
  light_infantry: 2,
  bow_infantry: 2,
  pikemen: 2,

  regular_infantry: 3,
  crossbow_infantry: 3,
  sappers: 3,
  raid_troops: 3,

  noble_infantry: 4,
  shock_troops: 4,
  field_engineers: 4,
}

Contraintes :
- exactement les 15 unités prototype ;
- pas de legacy ;
- pas de rangers ;
- pas de scout singulier.

2. Lire le niveau de caserne depuis la ville sélectionnée

Utiliser :

city.buildingLevels?.barracks ?? 0

ou l’équivalent selon le type réel.

Clamper défensivement :
- niveau minimal 0 ;
- niveau maximal 4.

3. Adapter l’état disabled des boutons

Un bouton de recrutement doit être désactivé si :

- pas de caserne ou niveau insuffisant ;
- ressources insuffisantes ;
- production déjà active ;
- coût serveur absent ou non chargé, selon logique existante ;
- autre blocage existant.

Important :
- ne pas supprimer les validations existantes ;
- ajouter le verrou caserne comme condition supplémentaire ;
- garder le serveur comme garde finale.

4. Ajouter indication visuelle du verrou

Pour chaque unité :
- afficher “Caserne Nv.X requise” si barracksLevel < requiredLevel.
- si barracksLevel >= requiredLevel, afficher l’état normal.

Exemples :
- sans caserne, militia : “Caserne Nv.1 requise”
- barracks N1, pikemen : “Caserne Nv.2 requise”
- barracks N2, noble_infantry : “Caserne Nv.4 requise”

5. Ajouter bannière globale

En haut du panneau :

Si barracksLevel = 0 :
- “Construisez une caserne pour recruter des unités.”

Si barracksLevel > 0 :
- “Caserne niveau X — unités débloquées jusqu’au niveau X.”

Ne pas prétendre que des unités sont disponibles si production active ou ressources insuffisantes.

6. Gérer les erreurs serveur

Si le serveur retourne :
- BARRACKS_REQUIRED
- BARRACKS_LEVEL_TOO_LOW

Afficher un message utilisateur clair.

But :
- Si les données client sont périmées, le serveur peut refuser.
- L’UI doit alors afficher l’erreur et idéalement relancer hydrateCitiesFromServer() si ce pattern existe déjà.

7. RecruitmentPanelZustand

Ce panneau est actif via CityManagementPanel selon V3-D6-G.

Donc :
- vérifier s’il affiche encore un flux de recrutement parallèle.
- appliquer le même verrouillage caserne minimal si nécessaire.
- éviter qu’il permette un clic qui déclenche ensuite inutilement 403 serveur.
- ne pas réintroduire legacy.

Si RecruitmentPanelZustand est clairement obsolète mais encore rendu :
- ne pas le supprimer dans ce bloc.
- le rendre cohérent avec le niveau de caserne.
- documenter qu’il doit être consolidé plus tard.

8. Types

Si City type côté client ne contient pas encore buildingLevels :
- l’ajouter de manière rétrocompatible.
- ne pas casser les DTO existants.
- buildingLevels?: Record<string, number> acceptable si nécessaire.
