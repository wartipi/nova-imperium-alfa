OBJECTIF 1 — Vérifier l’accès UI au recrutement

Vérifier concrètement comment un joueur ouvre le recrutement.

Documenter :
- depuis quel panneau ;
- quel bouton/onglet ;
- quel composant est rendu ;
- si RecruitmentPanel et RecruitmentPanelZustand sont tous deux visibles ou non ;
- si le bouton “Recruter” est assez clair ;
- si le coût de recrutement est visible.

Si l’accès est ambigu :
- micro-correction autorisée pour rendre l’accès clair.
- Exemples acceptables :
  - renommer un onglet/bouton “Unités” en “Recrutement” ;
  - ajouter un sous-titre “Cliquez sur Recruter pour former cette unité” ;
  - rendre le bouton “Recruter” plus explicite ;
  - ajouter une mention “Production de ville : une seule production active à la fois”.

Ne pas refactorer CityManagementPanel.

OBJECTIF 2 — Vérifier l’affichage des coûts de recrutement

Le joueur doit voir clairement les ressources demandées pour chaque unité.

Les coûts à afficher doivent venir du serveur via GET /recruitment-costs, ou du fallback déjà existant si le serveur n’a pas encore répondu.

Ne pas inventer de nouveaux coûts.

Ne pas afficher upkeep comme actif.

Si un texte d’entretien existe déjà :
- soit le retirer du panneau de recrutement actif ;
- soit le marquer explicitement comme “Entretien non activé” seulement si nécessaire.
- Préférence : ne pas afficher l’entretien pour l’instant.
