DÉCISION CANONIQUE — BÂTIMENTS

Tous les bâtiments de Nova Imperium doivent avoir 4 niveaux d’évolution.

Aucun bâtiment ne doit être ajouté comme bâtiment simple à niveau unique.

Tout nouveau bâtiment doit être pensé sous forme :

- Niveau 1
- Niveau 2
- Niveau 3
- Niveau 4

Chaque niveau peut :
- débloquer des fonctions ;
- améliorer des rendements ;
- améliorer des capacités ;
- débloquer des unités ;
- changer des coûts ou limites selon le système concerné.

DÉCISION CANONIQUE — CASERNE

La caserne doit devenir le bâtiment qui autorise le recrutement des unités terrestres.

La validation devra être serveur-authoritative dans un bloc futur.

Principe final attendu :

Sans caserne :
- aucune unité terrestre ne doit être recrutée ;
- le serveur doit refuser POST /start-recruitment ;
- aucun débit city_inventory ;
- aucune city_production créée ;
- l’UI doit afficher un message ou bloquer le recrutement.

Avec caserne :
- seules les unités débloquées par le niveau de caserne peuvent être recrutées.

OBJECTIFS DE L’AUDIT

1. Identifier comment les bâtiments sont représentés actuellement

Déterminer :
- s’ils sont stockés en DB ;
- dans quelle table ;
- sous quel format ;
- s’il y a un champ level/tier/niveau ;
- si les bâtiments sont attachés à une ville, une tuile, un joueur ou une faction ;
- comment on sait qu’une ville “possède” un bâtiment ;
- comment les bâtiments sont construits ;
- comment ils sont affichés ;
- comment leurs effets sont appliqués.

2. Identifier si le système supporte déjà les bâtiments à niveaux

Vérifier :
- présence d’un champ level ;
- présence d’un champ tier ;
- upgrade existant ou non ;
- coût par niveau existant ou non ;
- rendu UI par niveau existant ou non ;
- logique serveur par niveau existante ou non.

3. Identifier le chemin minimal pour ajouter une caserne à 4 niveaux

Produire un plan technique précis pour les blocs suivants :

V3-D7-B :
- ajouter la caserne niveaux 1–4 comme bâtiment canonique ;
- ne pas encore brancher le recrutement si préférable.

V3-D7-C :
- brancher la validation serveur start-recruitment selon niveau de caserne.

V3-D7-D :
- brancher l’UI RecruitmentPanel selon niveau de caserne.

V3-D7-E :
- tests end-to-end sans caserne / caserne N1 / N2 / N3 / N4.

4. Identifier les impacts DB

Dire clairement :
- si une migration DB sera nécessaire ;
- si le schema actuel supporte déjà les niveaux ;
- si une table existante peut être réutilisée ;
- si un nouveau champ est requis ;
- quels risques existent pour les données déjà présentes.

5. Identifier les impacts UI

Dire clairement :
- quel panneau de construction devra afficher la caserne ;
- comment montrer les 4 niveaux ;
- comment montrer les unités débloquées par niveau ;
- comment bloquer ou expliquer le recrutement sans caserne ;
- si RecruitmentPanel et RecruitmentPanelZustand doivent tous deux être modifiés.

6. Identifier les impacts serveur

Dire clairement :
- où ajouter la vérification “ville possède caserne niveau suffisant” ;
- si cette vérification doit être dans startRecruitmentTransaction ou avant son appel ;
- comment éviter tout débit si la caserne manque ;
- quel code d’erreur retourner :
  - 403 BARRACKS_REQUIRED ;
  - 403 BARRACKS_LEVEL_TOO_LOW ;
  - ou autre recommandation justifiée.
