À FAIRE

1. Créer ou ajouter les types serveur nécessaires

Créer dans un endroit approprié côté serveur, probablement dans `server/cityService.ts` ou un petit helper dédié si le code le justifie.

Type recommandé :

type RecruitmentCostResource =
  | "food"
  | "wood"
  | "stone"
  | "common_metals"
  | "common_textiles"
  | "labor_contracts"
  | "basic_equipment";

type RecruitmentResourceCost = Partial<Record<RecruitmentCostResource, number>>;

Important :
- Garder ce type serveur-local si importer CanonicalResourceId depuis shared/economicResources.ts crée trop de friction.
- Ne pas introduire de dépendance complexe.
- Ne pas modifier shared/economicResources.ts sauf nécessité stricte.

2. Ajouter une liste canonique serveur des ressources de recrutement

Créer une constante :

RECRUITMENT_COST_RESOURCES = [
  "food",
  "wood",
  "stone",
  "common_metals",
  "common_textiles",
  "labor_contracts",
  "basic_equipment",
] as const;

Utiliser cette liste pour éviter les boucles hardcodées dispersées.

3. Ajouter un helper normalizeRecruitmentCost

Créer un helper qui :

- accepte un objet partiel ;
- ignore les clés non autorisées ou les rejette explicitement, selon ce qui est plus sûr dans l’architecture actuelle ;
- convertit les valeurs null/undefined en absence ;
- refuse les valeurs négatives ;
- refuse les valeurs non entières ;
- retire les entrées à 0 ;
- retourne un objet propre.

Nom recommandé :

normalizeRecruitmentCost(cost: unknown): RecruitmentResourceCost

ou

validateRecruitmentCost(cost: unknown): RecruitmentResourceCost

Choisir le nom le plus cohérent avec le code existant.

4. Ajouter un helper de lecture de city_inventory

Créer un helper qui lit les stocks nécessaires dans `city_inventory`.

Nom recommandé :

getCityInventoryForRecruitment(cityId: number)

Doit retourner au minimum :

- cityId
- food
- wood
- stone
- common_metals
- common_textiles
- labor_contracts
- basic_equipment

Fallback à 0 si champ absent/null.

Important :
- Ne pas créer d’inventaire automatiquement si l’architecture actuelle ne le fait pas déjà.
- Si une ligne city_inventory absente doit être traitée comme stock 0, documenter ce choix.

5. Ajouter un helper canAffordRecruitmentCost

Créer un helper pur ou quasi-pur qui compare stock et coût.

Nom recommandé :

canAffordRecruitmentCost(inventory, cost)

Doit retourner une structure exploitable plus tard, par exemple :

{
  ok: boolean;
  missing: Array<{
    resource: RecruitmentCostResource;
    required: number;
    available: number;
    shortage: number;
  }>;
}

Important :
- Ne pas throw pour insuffisance normale.
- Retourner les détails pour que la future route puisse afficher une erreur propre.

6. Ajouter un helper de débit atomique

Créer le helper serveur futur :

debitCityInventoryForRecruitment(cityId: number, cost: RecruitmentResourceCost, tx?: any)

Comportement requis :

- utiliser une transaction si tx non fourni, ou utiliser tx si fourni ;
- normaliser/valider le coût ;
- lire l’inventaire actuel ;
- vérifier tous les montants ;
- si une ressource manque : ne rien débiter ;
- retourner une erreur structurée ou throw une erreur métier claire ;
- si tout est suffisant : débiter toutes les ressources en une seule opération logique ;
- mettre updatedAt à now ;
- retourner :
  - ok: true
  - debited cost
  - inventoryBefore optionnel
  - inventoryAfter optionnel si simple à obtenir

Approche recommandée :
- Pour ce bloc passif, privilégier lisibilité et sécurité.
- Utiliser une transaction.
- Éviter les updates partiels hors transaction.
- Ne pas optimiser prématurément.

7. Ajouter un helper previewRecruitmentCostPayment

Optionnel mais utile :
