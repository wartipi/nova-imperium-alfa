NOVA IMPERIUM — PROMPT D’IMPLÉMENTATION ÉLARGI (MARKETPLACE + ÉCONOMIE)

Branche :
NI-10.3

Contexte technique :
Jeu persistant Node/TS + React/TS + PostgreSQL
Architecture serveur autoritaire
Méthode stricte : audit → validation locale → implémentation minimale → vérification
Aucun refactor massif

OBJECTIF
Corriger proprement le flux d’achat marketplace pour qu’il utilise l’économie réelle de faction côté serveur, puis renforcer la cohérence inventaire / marketplace sans changer l’architecture.

CIBLE FONCTIONNELLE
Quand un joueur achète un item en vente directe :
1. le serveur identifie le joueur via l’auth réelle,
2. le serveur résout sa faction,
3. le serveur lit l’or réel de faction,
4. l’achat échoue si les fonds sont insuffisants,
5. l’or est débité une seule fois en base si l’achat réussit,
6. l’objet est transféré proprement du vendeur vers l’acheteur,
7. les metadata de l’objet sont conservées,
8. le client ne déduit plus l’or localement.

IMPORTANT
On garde les endpoints et la structure existante autant que possible.
On ne refond pas tout le marketplace.
On ne change pas l’architecture auth.
On ne touche pas au tick économique hors besoin direct.
On fait le plus petit patch stable possible.

PROBLÈMES DÉJÀ IDENTIFIÉS
- POST /api/marketplace/purchase-integrated/:itemId utilise encore un gold simulé.
- La route d’achat n’est pas branchée sur requireAuth.
- Le buyer est encore piloté par le body au lieu de l’identité authentifiée.
- Le client vérifie et dépense encore l’or localement.
- PublicMarketplace est monté avec playerId="player" en dur.
- Lors d’un achat d’objet unique, metadata est écrasé par {}.
- Le transfert d’objet est encore approximatif et ne garantit pas un vrai passage vendeur → acheteur.

CONTRAINTES
- Pas de refactor massif.
- Pas de nouveau système global.
- Pas de nouvelle architecture de données.
- Pas de duplication inutile.
- Le serveur doit rester source de vérité pour la dépense d’or.
- Préserver les comportements actuels hors périmètre.
- Rester lisible, déterministe, stable.

ÉTAPE 2 — AJOUTER UN DÉBIT RÉEL DE GOLD CÔTÉ ÉCONOMIE
Dans server/economyService.ts, ajouter une fonction dédiée du style :

debitFactionGoldIfEnough(factionId: number, amount: number)

Comportement attendu :
- amount > 0
- lecture/initialisation de faction_economy si nécessaire
- si gold < amount : success false + état courant
- sinon update réel de gold
- si possible, faire l’update avec garde gold >= amount pour éviter une double dépense concurrente
- retourner un résultat clair : success, goldBefore, goldAfter

Ajouter aussi, si nécessaire pour rollback minimal, une fonction inverse simple du style :
creditFactionGold(factionId: number, amount: number)

IMPORTANT :
pas de sur-ingénierie
pas de nouveau service séparé
juste le minimum propre

ÉTAPE 3 — BRANCHER LA ROUTE D’ACHAT SUR L’AUTH RÉELLE

POST /api/marketplace/purchase-integrated/:itemId

Attendu :

IMPORTANT :
