CONTEXTE VALIDÉ
Le comportement actuel du widget est encore incorrect en fin de trajet :

Exemple observé :
- Tuile 3 / 4
- Prochaine tuile encore affichée
- Avant prochaine case = 0s
- Trajet complet restant = Finalisation…

Ce comportement est faux pour l’utilisateur :
tant qu’une prochaine case reste à franchir, le timer "Avant prochaine case" ne doit pas déjà être à 0,
et "Trajet complet restant" ne doit pas déjà être en Finalisation si le trajet n’est pas encore entièrement consommé.

RÈGLE MÉTIER UI ATTENDUE
Je veux exactement ceci :

1. "Avant prochaine case"
= le temps restant du step/case actuellement confirmé
jusqu’au passage à la prochaine case

2. "Trajet complet restant"
= le temps estimé restant pour l’ordre complet si le trajet n’est pas interrompu
= temps du step courant restant
+ temps de tous les steps restants après celui-ci

IMPORTANT
Je ne veux plus que l’affichage principal repose directement sur msLeft seul
quand cela crée un 0s / Finalisation prématuré alors que le serveur confirme encore une case courante non terminée.

INTERPRÉTATION ATTENDUE
Aujourd’hui, côté serveur :
- 1 AP = 5 secondes
- le path contient un cost par step

Donc côté widget :
- durée d’un step = path[i].cost * msPerAP
- restant global = somme des coûts restants * msPerAP,
avec prise en compte du temps déjà écoulé dans le step courant confirmé

IMPORTANT
Tu peux dériver msPerAP depuis :
- totalDur / totalCost
pour rester aligné sur le serveur
mais le résultat attendu correspond bien à “PA restants x 5 secondes” dans la configuration actuelle.

MODIFICATION EXACTE ATTENDUE

OBJECTIF TECHNIQUE
Introduire une notion locale de "début du step confirmé courant" dans le widget.

COMPORTEMENT ATTENDU
A. Quand une nouvelle action move commence :
- initialiser le step courant confirmé
- initialiser le timestamp de début du step courant

B. Quand le widget reçoit nova:step-progress avec un effectiveStep plus grand :
- mettre à jour serverStep
- réinitialiser le timestamp de début du nouveau step confirmé

C. Calculer ensuite :
1. currentStepCost
   = coût du prochain passage depuis la case courante confirmée
   = path[currentStep + 1].cost si une prochaine case existe

2. msUntilNext
   = currentStepCost * msPerAP - temps écoulé depuis le début du step courant
   clampé à >= 0

3. remainingCostAfterNext
   = somme des coûts path[i].cost pour les steps après le prochain

4. journeyRemainingMs
   = msUntilNext + remainingCostAfterNext * msPerAP

IMPORTANT
Je veux que la ligne :
- "Avant prochaine case"
utilise msUntilNext

Et que la ligne :
- "Trajet complet restant"
utilise journeyRemainingMs
