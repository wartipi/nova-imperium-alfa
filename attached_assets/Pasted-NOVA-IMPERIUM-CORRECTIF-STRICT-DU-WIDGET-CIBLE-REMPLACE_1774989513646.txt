CONTEXTE VALIDÉ
Le correctif actuel utilise :
- isStartingPhase = msSinceStart < 3000
- isServerStepReliable = serverStep !== null && !isStartingPhase
- isLastStep = isStartingPhase ? false : currentStep >= totalSteps

Ce correctif est insuffisant.
Le bug observé en runtime persiste :
au début d’un nouveau trajet, le widget peut encore afficher :
- Tuile N / N
- Arrivée imminente…
- Finalisation…

CAUSE RACINE VALIDÉE
Le vrai problème n’est pas “3 secondes”.
Le vrai problème est :
au départ d’une nouvelle action, aucun nova:step-progress n’a encore été reçu pour cette action.

Donc :
- serverStep ne doit pas être considéré fiable
- la branche terminale ne doit pas être accessible
tant qu’aucun step confirmé de l’action courante n’a été reçu

OBJECTIF
Remplacer la logique de garde basée sur le temps
par une logique de garde basée sur la confirmation réelle d’un step.
