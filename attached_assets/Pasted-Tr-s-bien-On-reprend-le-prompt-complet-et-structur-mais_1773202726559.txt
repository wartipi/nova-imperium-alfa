# Prompt pour l’IA — Stabilisation du spawn joueur (prototype)

## Contexte

Le projet **Nova Imperium** utilise une **carte persistante stockée en PostgreSQL**.

Les tuiles du monde sont stockées dans la table :

```text
map_tiles
```

Chaque tuile contient notamment :

```
world_x
world_y
terrain_type
is_walkable
```

La position des joueurs est stockée dans :

```text
player_positions
```

avec :

```
player_id
world_x
world_y
segment_x
segment_y
```

Cette position est utilisée pour :

* charger la position du joueur au démarrage
* calculer les déplacements
* exécuter les actions de gameplay

Suite à la migration récente vers une génération de terrain **archipel**, certaines positions sauvegardées peuvent se retrouver sur des tuiles d’eau.

---

# Objectif de cette tâche

Stabiliser **temporairement** le système de spawn pour le prototype.

Pour cette phase de développement :

* le spawn peut être **un point fixe**
* la logique doit rester **extrêmement simple**
* toute validation doit être **côté serveur**

Nous voulons éviter toute position joueur sur :

```
deep_water
shallow_water
```

---

# Architecture souhaitée

Le point de spawn prototype doit être **centralisé et facilement modifiable**.

La coordonnée ne doit **pas être hardcodée directement dans la logique métier**.

Elle doit être définie dans **une constante serveur unique**, par exemple :

```ts
SPAWN_POINTS = {
  prototypeDefault: { worldX: 25, worldY: 15 }
}
```

Puis utilisée via une fonction d’accès unique, par exemple :

```
getActiveSpawnPoint()
```

De cette façon, le spawn pourra être changé plus tard vers :

* l’île de Sancta
* la Nouvelle Colonie
* un spawn dépendant de la faction

sans modifier la logique du système.

---

# Règles de travail (très importantes)

Avant toute modification :

1️⃣ analyser le code existant
2️⃣ expliquer le pipeline de position joueur
3️⃣ proposer la correction
4️⃣ attendre validation

Tu **ne modifies rien avant validation**.

Autres contraintes :

* ne pas modifier les tables DB
* ne pas modifier les routes API
* ne pas modifier la structure de la carte
* ne pas ajouter de système complexe de recherche de spawn
* garder une logique simple et lisible
