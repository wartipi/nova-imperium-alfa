NOVA IMPERIUM — BLOC 1 — AUDIT D’ARCHITECTURE DU DÉPLACEMENT PROGRESSIF
Branche cible : NI-10.3

CONTEXTE
Je ne veux pas d’implémentation immédiate.
Je veux un audit d’architecture strict, précis, factuel, sans code.

Le problème n’est plus seulement visuel.
Je veux vérifier si le modèle actuel de déplacement est structurellement cohérent avec le futur du jeu.

CONSTATS DÉJÀ VALIDÉS
Aujourd’hui, le déplacement semble encore modélisé comme :
- une seule action serveur `move`
- un `path` complet calculé au départ
- un `expectedEndTime`
- puis une mise à jour réelle de position seulement à la fin de l’action

Le client, lui, essaie de rejouer visuellement le trajet case par case avec un tick local et une position visuelle temporaire.

Donc le serveur traite encore le déplacement comme une commande monolithique,
et le client simule le déplacement progressif.

C’est potentiellement incohérent avec le futur du jeu, car une action de déplacement pourrait plus tard :
- être interrompue par un autre joueur
- être stoppée par un événement
- devoir être recalculée
- devoir s’arrêter entre deux cases
- devoir exposer clairement la case courante réellement occupée

OBJECTIF DE L’AUDIT
Je veux que tu détermines si le modèle actuel doit rester :
- “une action unique + simulation visuelle client”
ou si on doit passer à un vrai :
- déplacement progressif serveur, case par case

IMPORTANT
Je veux un audit technique et architectural.
Je ne veux pas que tu codes.
Je ne veux pas de patch.
Je veux que tu lises, que tu identifies les blocages structurels, puis que tu recommandes le plus petit modèle propre pour le futur.

INTERDIT
- aucune implémentation
- aucun patch
- aucun refactor
- aucun changement de schéma
- aucune migration
- aucune modification UI
- aucune supposition sans vérification
- ne pas proposer immédiatement un “quick fix”

AUDIT DEMANDÉ

1. MODÈLE ACTUEL RÉEL — SERVEUR
Je veux que tu expliques précisément :
- comment une action `move` est créée
- ce qui est stocké dans la DB
- quand la position du joueur change réellement côté serveur
- si le serveur connaît une “case courante” pendant le trajet ou seulement départ/fin
- si le serveur exécute réellement le trajet case par case ou non

Je veux une réponse factuelle avec :
- fichier
- fonction
- bloc logique
- impact exact

2. MODÈLE ACTUEL RÉEL — CLIENT
Je veux que tu expliques précisément :
- comment le client affiche actuellement le déplacement
- quelle est la différence entre position canonique et position visuelle
- quel composant/store pilote l’avatar pendant un move
- si le client est en train de “rejouer” un trajet déjà décidé par le serveur
- où apparaissent les désynchronisations possibles

Je veux distinguer clairement :
- état serveur réel
- état client simulé

3. PATHFINDER — CE QU’IL CHERCHE VRAIMENT
Je veux que tu confirmes précisément si le pathfinder serveur cherche :
- le chemin de coût total minimal en PA
ou
- le moins de cases
ou
- autre chose

Je veux aussi que tu me dises si ce comportement est cohérent avec un futur système de déplacement progressif.

4. COMPATIBILITÉ AVEC LE FUTUR DU JEU
Je veux que tu analyses explicitement si le modèle actuel est compatible avec ces besoins futurs :

- interruption par un autre joueur
- interruption par un événement
- arrêt du trajet à une case intermédiaire
- recalcul du chemin restant
- occupation réelle d’une case donnée à un instant t
- affichage visuel du chemin emprunté
- possibilité d’exposer “la prochaine case” ou “la case courante”
- résolution de conflits sur une route

Pour chaque point :
- compatible
- partiellement compatible
- incompatible
- et pourquoi

5. OPTIONS D’ARCHITECTURE
Je veux que tu évalues au minimum ces 3 options :

OPTION A — garder le modèle actuel
- une action move unique
- position réelle seulement à la fin
- client simule le trajet

OPTION B — une seule action move progressive
- path complet stocké
- progression serveur par étapes
- position réelle mise à jour à chaque case
- action toujours unique, mais avec step courant

OPTION C — une action par case
- le trajet complet est découpé en sous-actions unitaires

Pour chaque option :
- avantages
- inconvénients
- complexité
- robustesse
- compatibilité avec interruptions futures
- impact probable sur schéma / routes / client

6. RECOMMANDATION ARCHITECTURALE
Je veux que tu choisisses une option recommandée.
Tu dois prendre position clairement.

Je veux que tu expliques :
- pourquoi c’est le meilleur choix pour Nova Imperium
- pourquoi c’est le plus cohérent avec une architecture serveur-authoritative
- pourquoi c’est le plus petit passage propre possible
- pourquoi les autres options sont moins bonnes

IMPORTANT
Ne reste pas neutre.
Je veux une recommandation ferme.
