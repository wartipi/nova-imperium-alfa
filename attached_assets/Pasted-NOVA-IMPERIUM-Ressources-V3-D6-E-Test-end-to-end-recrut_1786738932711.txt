TESTS À EFFECTUER

1. Test endpoint coûts

Vérifier que :

GET /api/cities/recruitment-costs

retourne bien au minimum :

- militia
- garrison
- scouts
- hunters
- pikemen

Confirmer que les coûts/durées correspondent à RUNTIME_RECRUITMENT_COSTS.

2. Test start-recruitment prototype

Avec une ville accessible au joueur et un inventaire suffisant, tester :

POST /api/cities/:cityId/start-recruitment
body:
{ "unitType": "militia" }

Résultat attendu :
- 201
- ok: true
- unitType: "militia"
- debited contient food + labor_contracts
- production.name ou productionName = "militia"
- production.cost ou productionCost = durée en tours
- city_inventory décrémenté
- city_production créée

3. Test erreur ressources insuffisantes

Avec inventaire insuffisant, tester militia ou garrison.

Résultat attendu :
- 400
- error: "INSUFFICIENT_CITY_INVENTORY"
- missing[] lisible
- aucun city_production créé
- aucun débit partiel

4. Test production active

Tenter de lancer un second recrutement pendant qu’une production est déjà active.

Résultat attendu :
- 409
- error: "PRODUCTION_ALREADY_ACTIVE"
- aucun second débit

5. Test production tick

Faire avancer la production jusqu’à complétion.

Résultat attendu :
- productionProgress avance
- à complétion, createProducedUnit() reçoit "militia"
- UNIT_CATALOG["militia"] est trouvé
- une unité est insérée dans units
- city_production est vidée ou marquée terminée selon le comportement actuel
- aucune erreur silencieuse

6. Test affichage UI après création

Vérifier que l’unité créée apparaît dans l’armée actuelle.

Résultat attendu :
- type/id affiché sans crash
- icône fallback ou prototype correcte
- anciennes unités déjà existantes en DB restent affichables si présentes

7. Test non-régression legacy temporaire

Ne pas tester l’ancien flux comme état final.
Seulement vérifier qu’aucune erreur serveur n’est introduite par leur présence temporaire.
