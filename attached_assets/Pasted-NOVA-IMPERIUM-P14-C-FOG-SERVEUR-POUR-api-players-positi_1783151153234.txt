QUESTION PRINCIPALE

Existe-t-il déjà côté serveur une source fiable permettant de savoir si un joueur demandeur peut voir une case ?

Cas possibles :

A. Oui, une source serveur fiable existe déjà
- utiliser cette source
- filtrer `/api/players/positions` côté serveur
- ne renvoyer que les joueurs visibles

B. Source partielle seulement
- ex. tuiles découvertes persistées mais vision courante non disponible
- appliquer le filtre serveur le plus conservateur possible
- documenter clairement la limite

C. Aucune source fiable exploitable
- ne pas inventer un système complet
- ne pas modifier le serveur à l’aveugle
- produire un rapport d’audit précis
- proposer le plus petit prochain bloc nécessaire

RÈGLE DE SÉCURITÉ

En cas de doute :
- ne pas renvoyer la position de l’autre joueur
- préférer cacher plutôt qu’exposer
- aucun fallback permissif

RÈGLE ADMIN

Vérifier s’il existe déjà une notion fiable d’admin côté serveur pour la requête.

Si oui :
- un admin authentifié peut éventuellement recevoir toutes les positions, seulement si ce comportement existe déjà clairement et est cohérent avec le reste du projet

Si non :
- ne pas inventer un bypass admin serveur
- filtrer comme joueur normal

CORRECTION ATTENDUE SI SOURCE FIABLE DISPONIBLE

Dans ou avant `getActivePlayerPositions()` / route `/api/players/positions` :

1. Identifier le joueur demandeur depuis la session/auth existante.
2. Identifier sa position serveur si nécessaire.
3. Charger les données de visibilité existantes du joueur demandeur.
4. Pour chaque autre joueur actif :
   - convertir ou comparer avec les bonnes coordonnées monde/locales
   - vérifier si la tuile de l’autre joueur est visible ou au minimum découverte selon la source serveur existante
   - exclure tout joueur non visible
5. Retourner uniquement les joueurs visibles.
6. Ne jamais retourner une position hors visibilité à un joueur normal.

POINTS DE VIGILANCE COORDONNÉES

Attention aux conversions :
- l’API retourne des positions en coordonnées monde
- le client convertit ensuite avec `originWorldX/originWorldY`
- le filtre serveur doit utiliser les coordonnées attendues par les données persistées
- ne pas mélanger monde/local sans vérification

POINTS DE VIGILANCE PERFORMANCE

- Ne pas faire une requête DB par joueur si une requête groupée simple existe
- Mais ne pas introduire de cache complexe
- Préférer une solution simple et lisible
