CONTEXTE VALIDÉ
L’audit économique a confirmé 5 conteneurs réels :

1. player_bank
- réseau bancaire joueur
- alimenté par les villes avec banque
- débité par transfer_bank_to_city et transfer_bank_to_player

2. city_pending_harvest
- production accumulée des villes sans banque
- débité par collect_harvest

3. city_inventory
- stock local physique de la ville
- alimenté par collect_harvest et transfer_bank_to_city
- débité par les coûts de construction

4. player_transport
- ressources physiquement portées par le joueur
- alimenté par transfer_bank_to_player
- PROBLÈME ACTUEL : aucun débit réel branché

5. faction_economy
- legacy
- hors cible pour cette tâche

ÉTAT ACTUEL VALIDÉ
- TreasuryPanel = réseau bancaire
- HarvestPanel = inventaires locaux des villes
- PlayerTransportPanel = inventaire de transport du joueur
- MAIS player_transport reste un cul-de-sac
- donc l’économie n’est pas encore fermée proprement
- et les futurs tests de marché seraient pollués par cette ambiguïté

CONTRAINTE UI IMPORTANTE À RESPECTER
La section “Récolte des villes / inventaire local des villes” appartient logiquement au panneau :
- GESTION VILLE / TERRITOIRE

Je ne veux pas renforcer l’idée qu’elle doit vivre durablement comme panneau autonome séparé.
Donc dans cette tâche :
- ne pas créer une nouvelle architecture qui éloigne davantage la récolte des villes du panneau territoire
- si un ajustement UI est nécessaire pour refléter le dépôt vers city_inventory, il doit rester compatible avec cette cible
- ne pas consolider HarvestPanel comme destination finale de design
- considérer HarvestPanel comme transitoire / intermédiaire si nécessaire

OBJECTIF DE CETTE TÂCHE
Je veux ajouter le premier flux canonique de sortie de player_transport.

Je veux :
player_transport → city_inventory

But exact :
- le joueur transporte physiquement des ressources
- il se rend physiquement dans une ville
- il dépose une quantité choisie de son transport dans l’inventaire local de cette ville

IMPORTANT
Cette tâche NE porte PAS encore sur le marché.
Cette tâche prépare la base canonique avant les tests du marché.

RÈGLE MÉTIER CIBLE
Le dépôt depuis player_transport vers city_inventory doit être possible uniquement si :
- le joueur est physiquement sur une case de ville valide
- cette ville est la destination réelle du dépôt
- les quantités demandées existent réellement dans player_transport

Le résultat attendu :
- débit atomique de player_transport
- crédit atomique de city_inventory
- aucune approximation client
- aucune écriture directe côté client
- aucun bypass implicite

IMPORTANT
Je veux que la règle d’accès soit physique et canonique.
Pas un select global libre des villes.
Pas un menu qui montre toutes les villes.
Pas un dépôt à distance.

PHASE 3 — IMPLÉMENTATION SERVEUR

1. identifier le joueur via auth serveur
2. déterminer la ville réelle de dépôt depuis la position du joueur
3. refuser si le joueur n’est pas sur une ville valide
4. refuser si les quantités sont nulles
5. refuser si les quantités demandées dépassent player_transport
6. effectuer le mouvement de ressources dans une transaction atomique
7. retourner un payload simple et lisible
