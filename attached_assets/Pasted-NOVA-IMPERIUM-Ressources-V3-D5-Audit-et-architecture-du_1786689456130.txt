PROBLÈME ACTUEL

Le système de recrutement existant semble encore basé sur :

- productionCost: number
- productionProgress
- file de production ville
- création d’unité à la fin de production

Mais les unités prototype dans shared/landUnitCatalog.ts utilisent maintenant :

- creationCost: Partial<Record<CanonicalResourceId, number>>
- upkeepPerTurn
- maxMovementPerTurn
- actionPointCostPerTile
- siegeWearPoints
- creationProfile
- creationCategory

Le futur recrutement doit donc devenir serveur-authoritative et débiter plusieurs ressources réelles depuis un stock autorisé.

3. Source du paiement

Déterminer quel stock doit payer les coûts de recrutement.

Options à comparer :

A. city_inventory
- logique : la ville recrute avec son stock local
- avantage : logistique locale forte
- risque : il faut déposer les ressources en ville

B. player_bank
- logique : recrutement payé par banque centrale du joueur
- avantage : simple
- risque : moins stratégique/logistique

C. hybride
- ville paie les ressources matérielles
- banque paie fracten / contrats / ressources globales
- risque : complexité

Recommandation attendue :
Pour le prototype, recommander une approche simple et robuste, probablement city_inventory comme source principale, sauf si l’architecture actuelle rend cela trop risqué.

6. Interaction avec productionCost:number

Déterminer comment gérer l’ancien système :

Option A — conserver productionCost comme durée/progression uniquement
- les ressources sont débitées au lancement ;
- productionCost reste le temps/coût de production abstrait ;
- avantage : moins de refactor ;
- risque : le nom productionCost devient ambigu.

Option B — remplacer productionCost par productionDuration ou productionPointsRequired
- plus propre ;
- risque : migration plus lourde.

Option C — ajouter un champ metadata/resourceCost dans city_production
- permet garder compatibilité ;
- risque : nécessite adaptation.

Recommander l’option la plus sûre pour un premier branchement.
