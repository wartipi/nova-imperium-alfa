CONTEXTE VALIDÉ
Le modèle actuel de déplacement est trop monolithique :
- une action `move` unique
- un `path` complet
- une position réelle surtout mise à jour à la fin
- une progression encore trop dépendante du client pour être exploitable proprement

La direction validée est un modèle hybride :
- une seule action parent `move`
- le pathfinder reste uniquement calculateur de route
- la progression devient exploitable par step côté serveur
- le serveur doit pouvoir répondre à : “où est ce joueur maintenant ?”
- sans dépendre d’un calcul autonome du client

IMPORTANT
Dans cette phase, je ne veux PAS encore d’adaptation client.
Je veux poser uniquement la base serveur propre.

IMPLÉMENTATION ATTENDUE

LOT 1 — SCHÉMA MINIMAL
Fichier :
- shared/schema.ts

Ajout unique autorisé dans `playerActions` :
- `lastAppliedStep: integer("last_applied_step")`

Contraintes :
- nullable
- pas de default explicite
- pas d’autre colonne
- pas d’autre modification de schéma

Sémantique :
- `null` = aucun step intermédiaire encore persisté
- `0` ou plus = index du dernier step effectivement appliqué à `player_positions`
- ne peut jamais régresser

Après modification :
- pousser le schéma proprement

LOT 2 — RÉSOLVEUR PUR
Fichier :
- server/playerActionService.ts

Ajouter une fonction pure exportée :

- `resolveMoveStep(action, now)`

Contraintes :
- aucune lecture DB
- aucune écriture DB
- aucun effet de bord
- purement déterministe depuis `action` + `now`

Retour minimal attendu :
- `effectiveStep`
- `effectiveWorldX`
- `effectiveWorldY`
- `effectiveTerrain`
- `isCompleted`

Règles :
- utiliser `path`
- utiliser `startTime`
- utiliser `expectedEndTime`
- utiliser les coûts des steps
- `path[0]` = départ
- si trajet fini = dernier step
- si path trop court = step 0

LOT 3 — POINT D’ENTRÉE CENTRAL SERVEUR
Fichier :
- server/playerActionService.ts

Ajouter une fonction exportée :

- `resolveEffectivePlayerPosition(playerId, now)`

Rôle :
- si aucune action `move` active :
  - retourner la position depuis `player_positions`
- si une action `move` active :
  - utiliser `resolveMoveStep`
  - retourner la position effective calculée

IMPORTANT
Cette fonction est le point d’entrée central métier pour répondre à :
- “où est ce joueur maintenant ?”

Elle doit exister explicitement dans cette phase.
Elle ne doit pas être juste implicite dans `getActiveAction`.

LOT 4 — ADAPTATION DE getActiveAction
Fichier :
- server/playerActionService.ts

Comportement attendu :
1. lire l’action active
2. si expirée :
   - garder la complétion lazy actuelle
3. sinon, si `type === "move"` :
   - appeler `resolveMoveStep(row, now)`
   - comparer `effectiveStep` à `lastAppliedStep`
   - si `effectiveStep > (lastAppliedStep ?? -1)` :
     - `savePlayerPosition(...)` sur la case effective
     - `UPDATE player_actions SET lastAppliedStep = effectiveStep`
     - protéger l’UPDATE avec une garde contre régression / concurrence
4. retourner l’action enrichie avec :
   - `lastAppliedStep`
   - `effectiveStep`
   - `effectiveWorldX`
   - `effectiveWorldY`
   - `effectiveTerrain`

IMPORTANT
- ne pas casser les autres types d’actions
- ne pas changer `completeAction`
- ne pas changer la logique admin
- ne pas toucher au pathfinder

LOT 5 — ADAPTATION DE cancelActiveAction
Fichier :
- server/playerActionService.ts

Avant annulation :
- si action `move` active :
  - appeler `resolveMoveStep(activeAction, now)`
  - sauvegarder la position effective courante
  - écrire `lastAppliedStep` au step courant
- puis seulement :
  - `status = cancelled`

Règle métier :
- si l’annulation tombe entre deux steps, on retient le dernier step entièrement franchi
- jamais de position interpolée

LOT 6 — ROUTES SERVEUR
Fichier :
- server/routes/playerActions.ts

A. GET /api/player/actions/current
Enrichir la réponse JSON pour exposer :

- `lastAppliedStep`
- `effectiveStep`
- `effectiveWorldX`
- `effectiveWorldY`
- `effectiveTerrain`

Règles :
- présents pour les actions `move`
- ne pas casser l’existant
- garder réponse propre pour les autres actions

B. DELETE /api/player/actions/current
Enrichir la réponse avec :
- `cancelledAtWorldX`
- `cancelledAtWorldY`
- `cancelledAtStep`

Le but :
- permettre plus tard au client de se replacer immédiatement correctement
- même si cette phase ne touche pas encore le client
