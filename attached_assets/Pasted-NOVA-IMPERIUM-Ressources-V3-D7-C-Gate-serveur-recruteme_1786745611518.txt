DÉCISION CANONIQUE

Le recrutement terrestre nécessite une caserne.

Sans caserne :
- POST /start-recruitment doit refuser.
- Aucun débit city_inventory.
- Aucune city_production créée.

Avec caserne :
- le niveau de caserne détermine les unités recrutables.

À FAIRE — serveur

1. Créer un mapping serveur clair

Créer une constante serveur, idéalement près de la route ou dans un helper dédié :

BARRACKS_REQUIRED_LEVEL_BY_UNIT = {
  militia: 1,
  garrison: 1,
  scouts: 1,
  hunters: 1,

  patrollers: 2,
  light_infantry: 2,
  bow_infantry: 2,
  pikemen: 2,

  regular_infantry: 3,
  crossbow_infantry: 3,
  sappers: 3,
  raid_troops: 3,

  noble_infantry: 4,
  shock_troops: 4,
  field_engineers: 4,
}

Contraintes :
- utiliser les 15 IDs actifs seulement ;
- pas de legacy ;
- pas de rangers ;
- pas de scout singulier.

2. Lire le niveau de barracks de la ville

Utiliser la table city_buildings.

Comportement :
- si aucune ligne city_id + building='barracks' :
  - currentLevel = 0.
- sinon :
  - currentLevel = level.
- clamp défensif possible :
  - min 0 ;
  - max 4.

Ne pas dépendre seulement du DTO client.
La validation doit lire côté serveur/DB.

3. Ajouter une fonction/helper optionnel

Exemple de helper acceptable :

getCityBuildingLevel(cityId: number, building: string): Promise<number>

ou

getBarracksLevelForCity(cityId: number): Promise<number>

La fonction doit :
- interroger city_buildings ;
- retourner 0 si absent ;
- retourner level sinon ;
- ne pas modifier la DB.

4. Brancher la validation dans POST /start-recruitment

Avant startRecruitmentTransaction :

- requiredLevel = BARRACKS_REQUIRED_LEVEL_BY_UNIT[unitType]
- barracksLevel = await getBarracksLevelForCity(cityId)

Si barracksLevel <= 0 :
- return 403 BARRACKS_REQUIRED

Si barracksLevel < requiredLevel :
- return 403 BARRACKS_LEVEL_TOO_LOW

Sinon :
- continuer le flow existant.

5. Garantir l’absence de débit si refus

Important :
- La validation caserne doit se faire avant startRecruitmentTransaction.
- Aucun débit city_inventory ne doit être possible sur refus caserne.
- Aucune city_production ne doit être créée sur refus caserne.

6. Ne pas changer la logique de coûts

Ne pas modifier :
- RUNTIME_RECRUITMENT_COSTS
- normalizeRecruitmentCost
- debitCityInventoryForRecruitment
- startRecruitmentTransaction
- UNIT_CATALOG
- shared/landUnitCatalog.ts

Sauf si une micro-correction de type est absolument nécessaire, à documenter.
