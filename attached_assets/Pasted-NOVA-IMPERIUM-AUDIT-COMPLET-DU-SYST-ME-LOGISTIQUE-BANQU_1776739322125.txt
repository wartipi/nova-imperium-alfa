TRAVAIL À FAIRE

ÉTAPE 1 — AUDIT STRUCTURÉ DES FLUX

A. BANQUE → TRANSPORT JOUEUR
Vérifier :
- création d’action de transfert
- validation des quantités
- débit immédiat banque ou non
- destination réelle à la complétion
- refresh UI banque
- refresh UI transport
- timing exact appliqué
- messages côté client
- comportement si capacité insuffisante
- comportement si banque absente

B. TRANSPORT / BOÎTE MARCHÉ → BANQUE
Vérifier :
- collecte boîte marché vers banque
- gate physique banque
- crédit réel banque
- vidage réel boîte
- refresh UI cohérent
- messages cohérents

C. BOÎTE MARCHÉ → TRANSPORT
Vérifier :
- lecture de la boîte
- calcul de capacité
- refus si capacité insuffisante
- transfert réel vers transport
- vidage réel boîte
- refresh UI cohérent
- pas de duplication / perte silencieuse

D. BANQUE → VILLE
Vérifier :
- création d’action
- durée calculée
- cohérence avec computeTransportUnits si applicable
- complétion réelle
- destination réelle dans la ville
- messages et refreshs

E. CAPACITÉ TRANSPORT
Vérifier précisément :
- computeTransportUnits(...)
- or compressé : 1 unité = 250 or
- autres ressources : 1 unité chacune
- usedUnits / freeUnits backend
- affichage client
- cohérence entre capacité réelle et messages d’erreur
- cohérence entre capacité et dépôt boîte marché

F. TIMERS LOGISTIQUES
Vérifier précisément :
- banque → joueur
- banque → ville
- autres actions logistiques connexes encore actives
- s’il reste des anciennes formules non alignées
- si une durée utilise encore un calcul brut au lieu du calcul canonique

G. COMPLÉTION / REFRESH CLIENT
Vérifier :
- comment le client sait qu’une action logistique est terminée
- qui déclenche les refreshs banque / transport / boîte
- s’il existe encore des refreshs prématurés
- s’il faut reload manuel dans certains cas
- cohérence entre ActiveActionWidget, polling actions, et panneaux concernés

H. GATES D’ACCÈS
Vérifier :
- accès physique banque
- accès marché
- collecte boîte → banque
- lecture banque
- cohérence UI ↔ backend
- erreurs retournées si le joueur n’est pas au bon endroit

ÉTAPE 2 — CLASSIFICATION OBLIGATOIRE
Pour chaque point trouvé, classer explicitement dans une seule catégorie :
- VALIDÉ
- BUG CONFIRMÉ
- COMPORTEMENT ATTENDU
- ZONE FRAGILE
- DETTE TECHNIQUE NON BLOQUANTE

IMPORTANT
Ne mélange pas les catégories.

ÉTAPE 3 — PREUVES
Chaque validation importante ou problème doit s’appuyer sur une preuve directe :
- route
- fonction
- condition
- destination réelle des ressources/or
- état UI
- garde d’accès
- calcul de durée
- calcul d’unités
- refresh déclenché ou absent

Tu dois t’appuyer sur le code réellement poussé, pas sur les réponses précédentes.

ÉTAPE 4 — POINTS SPÉCIAUX À CONTRÔLER OBLIGATOIREMENT

POINT S1 — OR COMPRESSÉ
Confirmer noir sur blanc :
- où la règle 250 or = 1 unité est appliquée
- où elle est consommée
- si toute logique logistique critique est alignée dessus

POINT S2 — TIMERS
Confirmer noir sur blanc :
- si les durées banque → joueur et banque → ville sont cohérentes avec le calcul canonique d’unités
- ou s’il reste un décalage

POINT S3 — REFRESH À COMPLÉTION
Confirmer noir sur blanc :
- si les ressources transférées apparaissent sans reload manuel
- ou s’il reste des cas où un refresh manque ou part trop tôt

POINT S4 — PERTE SILENCIEUSE
Chercher explicitement s’il existe encore un cas où :
- une ressource/or quitte une source
- mais n’apparaît pas correctement à destination
- même de façon intermittente

ÉTAPE 6 — SORTIE ATTENDUE

Dans “DIAGNOSTIC GLOBAL” :
- dire honnêtement si le système logistique est globalement stable ou encore fragile
- dire si les problèmes restants sont critiques, moyens, ou secondaires

Dans “FLUX VALIDÉS” :
- lister seulement les flux réellement propres

Dans “PROBLÈMES CONFIRMÉS” :
- lister seulement les bugs réels prouvés

Dans “ZONES FRAGILES / À SURVEILLER” :
- lister les éléments techniquement fonctionnels mais à risque

Dans “LISTE PRIORISÉE DES CORRECTIFS RESTANTS” :
- produire une vraie séquence d’intervention
- du plus important au plus secondaire
- sans mélanger ce chantier avec d’autres systèmes non logistiques

CONTRAINTE FINALE
Le but exclusif est :
produire un audit complet, propre et priorisé du système logistique / banque / inventaire, afin de décider ensuite les prochains correctifs un par un.
