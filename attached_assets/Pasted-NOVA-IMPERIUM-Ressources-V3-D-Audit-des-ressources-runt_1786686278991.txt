OBJECTIFS DE L’AUDIT

1. Inspecter les fichiers liés aux ressources runtime :
   - shared/schema.ts
   - server/buildingEffects.ts
   - server/economyService.ts
   - server/cityService.ts
   - server/marketService.ts
   - server/playerActionService.ts
   - server/routes/economy.ts
   - server/routes/market.ts
   - client/src/lib/shared/ResourceIcons.ts
   - client/src/components/game/RecruitmentPanel.tsx
   - client/src/components/game/PublicMarketplace.tsx
   - tout autre fichier pertinent trouvé pendant l’audit

2. Identifier les ressources déjà supportées actuellement dans :
   - player_bank
   - city_inventory
   - city_pending_harvest
   - production par bâtiment
   - marché
   - transferts
   - affichage UI
   - coûts existants

3. Comparer les ressources runtime existantes avec les ressources nécessaires aux unités prototype.

Ressources nécessaires aux unités :

- food
- wood
- common_metals
- common_textiles
- labor_contracts
- basic_equipment

Pour chacune, déterminer :

- Existe-t-elle déjà en DB ?
- Existe-t-elle dans les inventaires joueur ?
- Existe-t-elle dans les inventaires ville ?
- Existe-t-elle dans les flux pending harvest ?
- Est-elle affichée dans l’UI ?
- Peut-elle être transférée ?
- Peut-elle être achetée/vendue au marché ?
- Peut-elle être produite par un bâtiment ?
- Est-elle utilisée dans un coût existant ?
- Quel est le risque de l’ajouter au runtime ?

4. Identifier les ressources V2 encore actives qui posent conflit conceptuel :
   - coal → devrait devenir fuel plus tard
   - oil → devrait devenir fuel plus tard
   - herbs → devrait devenir common_ingredients plus tard

Important :
Ne pas les renommer maintenant.
Seulement documenter les dépendances et risques.

5. Proposer un plan d’implémentation progressive, sans le coder.

Le plan devrait indiquer l’ordre recommandé pour rendre les coûts d’unités branchables.

Exemple d’ordre attendu :

- V3-D1 : audit actuel des ressources nécessaires aux unités
- V3-D2 : ajouter les ressources minimales manquantes en DB/inventaires si nécessaire
- V3-D3 : exposer ces ressources dans l’UI
- V3-D4 : ajouter production passive ou bâtiment source pour labor_contracts et basic_equipment
- V3-D5 : seulement ensuite brancher les coûts de recrutement depuis shared/landUnitCatalog.ts
