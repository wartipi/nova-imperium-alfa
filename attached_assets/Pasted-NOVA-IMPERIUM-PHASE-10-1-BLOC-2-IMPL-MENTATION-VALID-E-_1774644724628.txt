OBJECTIF
Fermer proprement le pipeline serveur-authoritative des unités :

ville → file de production → tick serveur → unité persistée → DTO serveur → hydratation client → toast de complétion

PÉRIMÈTRE STRICT
Tu implémentes uniquement :

* persistance canonique des unités produites
* ownership correct via `queuedByPlayerId`
* route serveur de lecture des unités
* hydratation client depuis le serveur
* toast de complétion unité
* compatibilité avec le pipeline bâtiments existant

Tu n’ouvres PAS :

* refonte armées
* combat
* déplacement avancé
* équilibrage
* abstraction générique
* nettoyage opportuniste hors sujet

DÉCISIONS VALIDÉES À RESPECTER

1. `city_production` reste la file canonique
2. ajout d’une table `units` minimale dans `shared/schema.ts`
3. ajout de `queuedByPlayerId` dans `city_production`
4. `strength` n’est PAS persisté en DB
5. `server/unitCatalog.ts` est la source canonique unique des stats de type
6. `GET /api/units/me` calcule `strength` côté serveur et renvoie un DTO directement hydratable
7. le client ne reconstruit pas localement les unités
8. fallback `queuedByPlayerId ?? playerId` autorisé uniquement pour compat legacy pré-migration, avec log serveur explicite
