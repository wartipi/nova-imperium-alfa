ÉTAT ACTUEL — DELTA À CORRIGER

Le patch logistique existe déjà, mais 3 incohérences restent ouvertes :

1. transfer-bank-to-city lit worldX/worldY depuis access.cityRecord, alors que checkCityAccess retourne encore la ligne cities.* au lieu d’exposer proprement les coordonnées réelles de la colonie.

2. ConstructionPanel continue à dépendre du vieux modèle client :
   - canAffordBuilding() vérifie encore currentNovaImperium.resources
   - handleBuild() continue à appeler buildInCity(... building.cost ...)
   Donc le nouveau modèle city_inventory coexiste encore avec l’ancien stock global abstrait.

3. Le modèle de capacité transport est incohérent entre backend et UI :
   - backend : max 50 unités totales
   - UI : texte “10 unités = 1 emplacement”
   Cette règle n’est pas réellement appliquée côté serveur.

OBJECTIF DE CE PATCH

Verrouiller proprement le modèle suivant :

- city_inventory = stock local canonique pour construire
- player_bank = réserve distante
- tout transfert depuis la banque prend du temps
- aucune construction ne dépend d’un stock global client abstrait
- UI et backend racontent exactement la même règle de transport

IMPORTANT

On ne refond pas tout.
On corrige uniquement les écarts structurels restants.
Je veux le plus petit patch propre possible.

RÈGLE DE DESIGN À VERROUILLER

1. La construction joueur doit dépendre uniquement de :
   - l’accès à la ville
   - la disponibilité des matériaux dans city_inventory
   - les contraintes de terrain / bâtiment
   - les PA si elles restent dans le modèle
2. Elle ne doit plus dépendre d’un stock global client.
3. Le client peut afficher des infos locales, mais le serveur reste la seule source de vérité pour les matériaux.
4. La capacité transport affichée doit être exactement celle validée côté serveur.

POINT 2 — PURGER CONSTRUCTIONPANEL DU VIEUX STOCK GLOBAL

Dans ConstructionPanel.tsx :

Je veux retirer la dépendance métier à currentNovaImperium.resources pour la construction joueur.

À faire :
- canAffordBuilding() ne doit plus refuser une construction joueur en fonction du stock global client
- conserver si nécessaire :
  - la vérification PA
  - la vérification terrain
  - la vérification “déjà construit / déjà en cours”
- mais ne plus utiliser les ressources globales comme vérité métier pour les matériaux

Dans handleBuild():
- l’appel serveur apiStartConstruction doit devenir la validation canonique des matériaux
- si le serveur dit INSUFFICIENT_CITY_INVENTORY :
  - afficher le message local déjà en place
  - ne pas lancer la construction
- si succès joueur :
  - ne pas réintroduire une déduction locale parallèle depuis un stock global
  - ne pas laisser buildInCity redéduire les coûts matériaux d’une autre source

IMPORTANT :
Si buildInCity attend encore building.cost pour des raisons historiques :
- adapter au plus petit patch propre
- par exemple lui passer un coût neutre pour la partie ressources si nécessaire
- ou extraire le strict minimum pour qu’il serve à l’état visuel / production sans refaire une deuxième consommation

But :
