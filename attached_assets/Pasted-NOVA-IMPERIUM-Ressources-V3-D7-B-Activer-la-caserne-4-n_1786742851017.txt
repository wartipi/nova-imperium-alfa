À FAIRE — serveur

1. Modifier addBuilding() ou la fonction équivalente

Comportement actuel :
- ON CONFLICT DO NOTHING.

Comportement attendu :
- Si le bâtiment n’existe pas encore dans la ville :
  - insérer building avec level = 1.
- Si le bâtiment existe déjà et level < 4 :
  - augmenter level de 1.
- Si le bâtiment existe déjà et level >= 4 :
  - refuser ou retourner un statut clair “MAX_LEVEL_REACHED”.
- Ne jamais dépasser level 4.

Approche recommandée :
- Utiliser ON CONFLICT(city_id, building) DO UPDATE.
- Mettre level = LEAST(city_buildings.level + 1, 4).
- Si le système permet de détecter le niveau avant/après, retourner clairement le nouveau niveau.
- Éviter les doubles upgrades accidentels si la fonction est appelée deux fois.

Important :
- Ne pas créer de migration DB.
- Ne pas changer le schema si level existe déjà.
- Ne pas supprimer la contrainte UNIQUE(city_id, building).

2. Exposer le level dans les lectures ville/bâtiments

Vérifier les DTO existants.

Si actuellement les bâtiments sont exposés comme string[] :
- conserver la compatibilité si nécessaire ;
- ajouter une structure complémentaire qui expose building + level ;
- ne pas casser les UI existantes.

Exemples acceptables selon le code existant :

Option A :
buildings: string[]
buildingLevels: Record<string, number>

Option B :
buildings: Array<{ building: string; level: number }>

Choisir l’option la moins intrusive selon le code actuel.

Important :
- Ne pas casser les panels existants.
- Documenter le format final retenu.

3. Ajouter barracks au catalogue/effets si nécessaire
