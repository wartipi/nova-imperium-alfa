OBJECTIF
Corriger uniquement le risque critique P0 :
dans completeAction(), l’action est actuellement marquée "completed" avant l’application de l’effet de bord réel (crédit destination / reset pending), ce qui peut produire une perte silencieuse ou une duplication si une erreur survient ensuite.

IMPORTANT
Ne traite PAS dans ce segment :
- P1 placeOrder transactionnel
- P2 createTransferBankToCityAction / createTransferBankToPlayerAction
- P3 cancelOrder
- autres chantiers marché
- admin bypass
- timers
- UI

On corrige uniquement la sûreté transactionnelle de completeAction() et, si nécessaire, la sûreté immédiate de completeHarvestTransfer() utilisée par ce flux.

FORMAT DE RÉPONSE OBLIGATOIRE
Réponds exactement avec :
1. DIAGNOSTIC
2. FICHIERS CONCERNÉS
3. MODIFICATION MINIMALE PROPOSÉE
4. PREUVE DIRECTE
5. VÉRIFICATION
6. STOP

FICHIERS À AUDITER
- server/playerActionService.ts

DIAGNOSTIC À RESPECTER
Le problème suspecté est :

A. completeAction() fait actuellement :
1. update playerActions → status="completed"
2. puis appelle l’effet de bord :
   - completeBankToCityTransfer(...)
   - ou completeBankToPlayerTransfer(...)
   - ou completeHarvestTransfer(...)

B. Si l’effet de bord échoue après le update status="completed" :
- l’action n’est plus in_progress
- getActiveAction() ne la retryera plus
- les ressources peuvent être perdues silencieusement
- ou, pour harvest, un demi-état peut apparaître

C. completeHarvestTransfer() lui-même semble faire :
1. crédit cityInventory
2. puis reset cityPendingHarvest
sans transaction englobante

OBJECTIF FONCTIONNEL EXACT
Garantir que :
- l’effet de bord de complétion et le passage à status="completed" soient atomiques
OU
- à défaut, si l’effet de bord échoue, l’action reste retryable et aucun demi-état silencieux n’est commité

Priorité absolue :
pas de perte silencieuse
pas de duplication silencieuse
pas d’action “completed” sans effet réel

IMPORTANT
