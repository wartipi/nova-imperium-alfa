ÉTAPE 1 — AUDIT RIVIÈRES / COURS D’EAU

Chercher si une vraie donnée “river” existe.

Inspecter :

* mapData
* HexTile / Tile types
* MapGenerator.ts
* mapAdapter.ts
* GameEngine.ts
* shared/schema.ts

Chercher les champs / termes :

* river
* rivers
* stream
* waterway
* creek
* lake
* shallow
* deep
* coast
* water

Distinguer clairement :

* eau existante comme terrain : deep_water / shallow_water / ocean / coast
* vraie rivière comme donnée distincte
* simple bordure entre terre/eau
* absence totale de rivière

Conclusion attendue :

* “rivières réelles disponibles”
  ou
* “seulement eau/terrain disponible, pas de vraie rivière”
  ou
* “aucune donnée exploitable”

Ne pas inventer de rivière à partir du terrain.

ÉTAPE 2 — AUDIT AVATAR / POSITION JOUEUR

Chercher si une position avatar distincte existe.

Inspecter :

* stores joueur
* GameCanvas.tsx
* GameEngine.ts
* types.ts
* usePlayer.tsx
* useNovaImperium.tsx

Chercher :

* avatar
* playerPosition
* currentPosition
* x/y joueur
* selectedUnit
* controlledUnit
* camera target
* spawn position
* player unit
* civilization position

Distinguer :

* avatar réel du joueur
* unité sélectionnée
* colonie du joueur
* caméra centrée sur une entité
* simple donnée de profil joueur

Conclusion attendue :

* “avatar réel disponible”
  ou
* “pas d’avatar distinct, seulement unités / colonies”
  ou
* “donnée ambiguë à ne pas rendre”

Ne pas créer d’avatar fictif.

ÉTAPE 3 — AUDIT AUTRES JOUEURS / MULTIJOUEUR

Chercher quelles données sur les autres joueurs sont chargées côté client.

Inspecter :

* stores
* GameCanvas.tsx
* GameEngine.ts
* routes API déjà utilisées côté client
* types
* données de colonies / territoires / unités

Identifier :

* autres joueurs visibles
* colonies d’autres joueurs
* unités d’autres joueurs
* ownership d’autres factions
* présence active / online status
* noms affichables
* données cachées par fog
* données admin-only

Règles :

* ne jamais proposer de rendre des infos qui brisent le fog
* ne jamais afficher des données admin-only en mode joueur normal
* ne jamais exposer la position d’un joueur caché

Conclusion attendue :

* ce qui est déjà affiché indirectement par ownership/colonies/unités
* ce qui peut être affiché sans danger
* ce qui doit attendre un système de visibilité multijoueur clair

ÉTAPE 4 — AUDIT ROUTES CONSTRUCTIBLES

Reprendre la conclusion P11 et cadrer le futur système de routes.

Confirmer :

* aucune colonne route dans shared/schema.ts
* hasRoad existe mais non alimenté
* road existe peut-être comme coût/bâtiment mais non utilisé comme système complet
* strategic n’affiche aucune route réelle

Définir si les routes doivent être :

* infrastructure construite par joueur
* infrastructure construite par faction/entité
* bâtiment de tuile
* amélioration de territoire
* réseau logistique
* effet sur déplacement
* effet sur commerce

Ne pas implémenter.

Produire seulement une recommandation de futur bloc système routes.

Classer chaque élément :

* déjà rendu

* pas disponible

* nécessite nouvelle logique

Ne pas ajouter ces rendus dans P13.
