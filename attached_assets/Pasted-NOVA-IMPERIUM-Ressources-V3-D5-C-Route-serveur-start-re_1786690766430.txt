OBJECTIF DE CE BLOC

Créer une route serveur :

POST /api/cities/:cityId/start-recruitment

Cette route doit :

1. vérifier l’accès à la ville ;
2. valider le payload ;
3. déterminer un coût multi-ressources serveur-side ;
4. débiter city_inventory via debitCityInventoryForRecruitment() ;
5. lancer la production existante via setProduction() ;
6. conserver productionCost:number comme durée/progression ;
7. retourner une réponse structurée.

IMPORTANT DESIGN

Pour ce bloc, ne pas brancher encore shared/landUnitCatalog.ts directement si cela crée un risque avec les IDs incompatibles.

Rappel audit :
- server/unitCatalog.ts utilise actuellement des IDs comme warrior/spearman/archer/...
- shared/landUnitCatalog.ts utilise militia/garrison/patrollers/...
- createProducedUnit() utilise UNIT_CATALOG serveur.
- Si on lance une unité prototype non présente dans server/unitCatalog.ts, la complétion échouera.

Donc pour V3-D5-C, la route doit rester compatible avec les unités runtime actuelles.

ROUTE À AJOUTER

POST /api/cities/:cityId/start-recruitment

Payload attendu :

{
  "unitType": "warrior"
}

Optionnel si nécessaire :

{
  "unitType": "warrior",
  "adminModeEnabled": false

Ne pas accepter de coût envoyé par le client comme source de vérité.
Le coût doit venir du serveur.

VALIDATIONS REQUISES

1. cityId
- doit être un entier valide.

2. Accès ville
- utiliser checkCityAccess(req.user!.id, cityId).
- retourner les erreurs existantes si accès refusé.

3. unitType
- requis.
- string.
- doit exister dans le catalogue runtime actuel qui sera utilisé à la complétion.
- vérifier contre server/unitCatalog.ts / UNIT_CATALOG ou helper existant.
- si inconnu : 400 avec erreur lisible.

4. Production déjà active
- vérifier s’il existe déjà une production en cours pour cette ville.
- si oui : refuser avec 409 ou 400.
- message clair : “Une production est déjà en cours dans cette ville.”
- Ne pas écraser silencieusement une production existante.

5. Coût multi-ressources
- récupérer le coût serveur depuis la table temporaire RUNTIME_RECRUITMENT_COSTS ou helper.
- utiliser uniquement les 7 ressources autorisées :
  - food
  - wood
  - stone
  - common_metals
  - common_textiles
  - labor_contracts
  - basic_equipment

6. Débit atomique
- appeler debitCityInventoryForRecruitment(cityId, cost).
- si erreur INSUFFICIENT_CITY_INVENTORY :
  - retourner 400
  - inclure missing[] dans la réponse.
- si autre erreur : 500.

7. Lancement production
- après débit réussi, appeler setProduction() avec :
  - type: "unit"
  - name: unitType
  - cost: recruitmentTime ou productionCost runtime actuel
  - progress: 0

Important :
- productionCost:number reste durée/progression.
- Ne pas renommer en productionDuration dans ce bloc.

8. Atomicité débit + setProduction

Point critique :
Le débit et setProduction doivent être aussi sûrs que possible.

Option minimale acceptable pour ce bloc :
- Vérifier production active AVANT débit.
- Débiter.
- Appeler setProduction().
- Si setProduction() échoue après débit, logguer clairement le risque.

Option préférable :
- Si possible, ajouter dans cityService ou route une transaction unique autour :
  - check production active
  - debit city_inventory
  - set city_production
Mais ne pas faire de refactor massif.

Si la transaction est trop risquée avec l’architecture actuelle :
- garder l’option minimale ;
- documenter explicitement le risque restant dans CLAUDE.md ;
- prévoir correction V3-D5-C2.

9. Réponse attendue

Succès :

{
  "ok": true,
  "cityId": 1,
  "unitType": "warrior",
  "production": {
    "type": "unit",
