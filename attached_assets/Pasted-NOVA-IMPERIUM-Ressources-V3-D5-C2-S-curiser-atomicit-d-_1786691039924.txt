PROBLÈME À RÉSOUDRE

Actuellement :

debitCityInventoryForRecruitment(cityId, cost)
await setProduction(cityId, ...)

Si setProduction() throw après le débit, il n’y a pas de rollback.

APPROCHE RECOMMANDÉE

Créer une fonction serveur dédiée dans `server/recruitmentService.ts` :

startRecruitmentTransaction(params)

ou nom équivalent.

Cette fonction doit faire, dans une seule transaction DB :

1. vérifier qu’aucune production n’est active pour la ville ;
2. débiter city_inventory avec garde SQL conditionnelle ;
3. insérer/upsert city_production ou appeler une variante transactionnelle de setProduction ;
4. retourner :
   - ok
   - debited
   - production

IMPORTANT TECHNIQUE

Le helper actuel `debitCityInventoryForRecruitment()` utilise `db` directement.

Pour permettre une transaction, ajouter une variante qui accepte un client transactionnel, par exemple :

debitCityInventoryForRecruitmentTx(tx, cityId, rawCost)

ou adapter le helper existant pour accepter un paramètre optionnel :

debitCityInventoryForRecruitment(cityId, rawCost, tx?)

Choisir l’approche la moins risquée.

Le code doit éviter de dupliquer toute la logique si possible, mais la priorité est la sûreté et la lisibilité.

TRANSACTION

Utiliser la transaction Drizzle disponible via `db.transaction` si supportée.

Structure attendue :

await db.transaction(async (tx) => {
  // check production active using tx
  // debit using tx
  // set production using tx or direct insert/update using tx
})

Si `setProduction()` ne peut pas accepter `tx`, créer une petite fonction interne transactionnelle qui écrit directement dans `city_production` avec la même structure que `setProduction()`.

Important :
- ne pas refactoriser tout cityService.ts ;
- ne pas modifier les routes existantes sauf start-recruitment ;
- ne pas casser PUT /production.

CHECK PRODUCTION ACTIVE

La vérification “production déjà active” doit être dans la transaction.

Si une production existe :
- throw une erreur métier ou retourner 409 depuis la route.
- Ne rien débiter.

DÉBIT

Le débit doit rester concurrence-safe :
- UPDATE conditionnel ;
- WHERE city_id = cityId ;
- AND ressource >= coût ;
- décréments SQL relatifs ;
- RETURNING.

Si le débit échoue :
- relire l’inventaire dans la transaction ou immédiatement après ;
- retourner/throw `INSUFFICIENT_CITY_INVENTORY` avec `missing[]`.

SET PRODUCTION

L’écriture dans `city_production` doit être dans la même transaction que le débit.

Utiliser les mêmes valeurs qu’en V3-D5-C :

{
  productionType: "unit",
  productionName: unitType,
  productionCost: recruitmentEntry.duration,
  productionProgress: 0
}

ou les noms exacts du schema Drizzle.

Ne pas modifier productionCost:number.
Il reste la durée/progression.
