Mise en situation — Phase 1 : Stabilisation admin et cartographie des dépendances avant multijoueur

Nova Imperium a déjà franchi plusieurs étapes importantes :

le vieux mode MJ client a été démantelé

l’authentification utilise maintenant le vrai rôle serveur

un mode admin ON/OFF existe côté client

le moteur visuel et une partie du serveur commencent à respecter ce mode

le déplacement persistant serveur fonctionne

le déplacement instantané admin peut être activé ou désactivé selon le contexte

Mais le projet reste dans une phase hybride.

Aujourd’hui, certains systèmes sont déjà partiellement propres, alors que d’autres restent encore :

très client-side

partiellement bypassés

ou pas encore reliés au nouveau modèle adminModeEnabled

Avant de continuer à brancher des validations serveur ou à préparer le multijoueur, il faut faire une phase de stabilisation.

Cette phase a un but très concret :

1. Cartographier précisément tous les bypass restants

On veut savoir :

ce qui dépend déjà de adminModeEnabled

ce qui dépend encore seulement de role === 'admin'

ce qui n’est pas encore intégré au nouveau modèle

2. Identifier les systèmes encore trop client-side

On veut savoir :

quels systèmes sont encore pilotés presque entièrement par le client

lesquels seront problématiques dès qu’on testera à plusieurs

3. Définir les priorités avant multijoueur

Le but n’est pas encore de tout réécrire.
Le but est de savoir :

quelles mécaniques doivent passer serveur en premier

lesquelles peuvent rester temporairement côté client

lesquelles risquent de casser ou de devenir incohérentes dès qu’on joue à plusieurs

4. Préparer la suite

Cette phase doit servir de base aux prochaines étapes :

propagation serveur plus large de adminModeEnabled

validation serveur des compétences

validation serveur des PA

migration des actions spéciales restantes

connectivité multijoueur / présence des autres joueurs

Donc cette Phase 1 n’est pas “une simple vérification”.

C’est un audit structurant de stabilité et de priorisation.

Prompt pour l’IA — Phase 1 : Stabilisation admin et cartographie avant multijoueur
Nouveau bloc de travail : Phase 1 — stabilisation du mode admin et cartographie des systèmes avant préparation multijoueur.

Contexte

Nova Imperium a déjà franchi plusieurs étapes importantes :

- le vieux mode MJ client a été supprimé comme source de vérité
- l’authentification utilise maintenant le vrai rôle serveur
- AuthContext expose role, adminModeEnabled et isAdmin
- un mode admin ON/OFF existe côté client
- le moteur visuel respecte ce mode via une injection propre
- le déplacement persistant serveur fonctionne
- le serveur respecte maintenant adminModeEnabled pour le bypass de timer de déplacement

Mais le projet reste dans une phase hybride.

Certains systèmes sont déjà correctement réalignés sur l’architecture actuelle.
D’autres restent encore :

- purement client-side
- partiellement bypassés
- non intégrés à adminModeEnabled
- non prêts pour un test multijoueur crédible

Objectif de la Phase 1

Je veux un audit structuré qui serve de fondation pour les prochaines étapes.

Cette phase doit permettre de :

1. cartographier tous les bypass/admin behaviors restants
2. identifier lesquels sont déjà branchés sur adminModeEnabled
3. identifier lesquels dépendent encore seulement de role === 'admin'
4. identifier quels systèmes sont encore trop client-side pour être fiables en multijoueur
5. définir un ordre de priorité technique avant les prochains blocs serveur et multijoueur

Important :
cette phase est un audit et une cartographie.
Tu ne modifies rien avant validation.

Règles de travail

Avant toute modification :

1. analyser le code réellement présent dans la branche actuelle
2. lister les systèmes concernés
3. classifier chaque système selon son état réel
4. distinguer :
   - ce qui est déjà propre
   - ce qui est encore hybride
   - ce qui est encore purement client-side
   - ce qui posera problème en multijoueur
5. proposer une priorisation claire
6. attendre validation

Tu ne modifies rien avant validation.

Contraintes

- ne pas faire d’implémentation dans cette phase
- ne pas proposer de refonte totale floue
- ne pas mélanger audit et correctif
- ne pas supposer le comportement sans preuve
- citer les fichiers, services, stores et routes exacts
- séparer clairement :
  - client
  - serveur
  - hybride
  - risque multijoueur

Exigence de rigueur

- pas de formulation vague
- pas de “probablement” sans preuve
- je veux des faits démontrés par le code
- si un système n’est pas clair, il faut le dire explicitement
