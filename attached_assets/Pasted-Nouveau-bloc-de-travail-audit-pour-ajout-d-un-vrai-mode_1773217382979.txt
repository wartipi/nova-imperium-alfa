Nouveau bloc de travail : audit pour ajout d’un vrai mode admin ON/OFF propre.

Contexte

Le vieux mode MJ client a été migré en grande partie vers une logique basée sur :

role === 'admin'

Les blocs précédents ont déjà été validés :

- suppression de isGameMaster et toggleGameMaster
- migration de la logique client vers role === 'admin'
- injection propre de l’état admin dans GameEngine via setAdminMode()
- suppression des hacks XP/compétences max
- nettoyage des comportements visuels admin
- nettoyage des vieux hacks gameplay admin résiduels

La situation actuelle est donc :

- le rôle serveur distingue admin et player
- plusieurs bypass utiles pour les tests dépendent maintenant directement de role === 'admin'

Problème actuel

Un compte admin bénéficie automatiquement de tous les bypass liés au test.

Cela a un inconvénient :
- il est impossible de tester facilement, avec le même compte admin, le comportement normal du jeu sans bypass
- il faut actuellement soit changer de compte, soit subir en permanence les privilèges admin

Objectif

Ajouter un vrai mode admin ON/OFF propre.

Important :
- le rôle serveur reste admin / player
- on n’ajoute pas un nouveau rôle
- on ajoute un flag d’exécution admin permettant d’activer ou désactiver les bypass de test
- ce flag ne doit pas recréer l’ancien mode MJ fantôme
- ce flag doit être intégré proprement à l’architecture existante

Direction souhaitée

À terme, les helpers du type :

shouldIgnoreActionTimers(context)
shouldIgnoreActionPointCosts(context)
shouldIgnoreCompetencePointCosts(context)
shouldRevealEntireMap(context)
shouldRevealAllResources(context)

ne doivent plus dépendre seulement de :

role === 'admin'

mais de quelque chose comme :

role === 'admin' && adminModeEnabled === true

Même idée côté client visuel :
- un admin peut choisir d’afficher ou non les privilèges de test

Règles de travail

Avant toute modification :

1. analyser l’architecture actuelle
2. identifier où un flag adminModeEnabled pourrait vivre proprement
3. identifier comment il devrait être propagé côté client et côté serveur
4. identifier les comportements qui devraient dépendre de ce flag
5. proposer une intégration minimale et cohérente
6. attendre validation

Tu ne modifies rien avant validation.

Contraintes :

- ne pas recréer un simple toggle local fantôme sans lien avec l’architecture
- ne pas introduire de hook React dans GameEngine
- ne pas changer le rôle serveur
- ne pas ajouter de nouveau rôle
- rester cohérent avec l’architecture actuelle :
  auth propre, GameEngine injecté, ActorContext déjà utilisé côté actions persistantes
- distinguer clairement ce qui devra être client-only, serveur-only, ou mixte

Exigence de rigueur :

- pas de formulation vague
- pas de supposition
- citer les fichiers et points d’injection exacts
- distinguer :
  - l’état actuel
  - la cible
  - le plus petit chemin cohérent
