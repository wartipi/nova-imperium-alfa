Prompt pour l’IA — Audit de propagation serveur de adminModeEnabled
Nouveau bloc de travail : audit de propagation serveur de adminModeEnabled.

Contexte

Le projet Nova Imperium a maintenant une base admin propre côté client :

- le vieux mode MJ client a été supprimé
- le rôle vient du serveur via l’authentification
- AuthContext expose maintenant :
  - role
  - adminModeEnabled
  - isAdmin = role === 'admin' && adminModeEnabled
- côté client, les bypass visuels et gameplay peuvent maintenant être activés ou désactivés avec un vrai toggle admin ON/OFF

État actuel du problème

Le backend, lui, ne connaît pas encore adminModeEnabled.

Aujourd’hui, les helpers serveur continuent de dépendre uniquement de :

role === 'admin'

Conséquence :
- un compte admin garde encore certains bypass serveur même si adminModeEnabled est OFF côté client
- par exemple les déplacements instantanés restent actifs côté serveur

Objectif de ce bloc

Identifier comment propager proprement adminModeEnabled côté serveur, sans recréer un système flou.

Nous voulons préparer une architecture où les helpers serveur du type :

shouldIgnoreActionTimers(context)
shouldIgnoreActionPointCosts(context)

pourront dépendre de :

context.role === 'admin' && context.adminModeEnabled === true

Important :
ce bloc est un audit et un plan de propagation.
Tu ne modifies rien avant validation.

Règles de travail

Avant toute modification :

1. analyser l’architecture actuelle de ActorContext et des routes concernées
2. identifier où adminModeEnabled devrait être transmis depuis le client
3. identifier comment il devrait être injecté dans ActorContext
4. identifier quels comportements serveur doivent dépendre de ce flag
5. proposer le plus petit chemin cohérent
6. attendre validation

Tu ne modifies rien avant validation.

Contraintes :

- ne pas changer le rôle serveur
- ne pas ajouter de nouveau rôle
- ne pas introduire de logique par username
- rester cohérent avec l’architecture actuelle :
  - AuthContext côté client
  - ActorContext côté serveur
  - playerActions.ts
  - playerActionService.ts
- ne pas prétendre sécuriser complètement le backend si ce bloc ne couvre pas encore tous les endpoints
- distinguer clairement ce qui sera vraiment corrigé dans ce bloc et ce qui restera pour plus tard

Exigence de rigueur :

- pas de formulation vague
- pas de supposition
- citer les fichiers et points d’injection exacts
- distinguer :
  - état actuel
  - cible
  - plus petit chemin cohérent
  - limites restantes
